# 성수 콘텐츠 관리 기능 기획서

2026-10-23 · @sungryeong

## 배경과 목적

현재 성수 콘텐츠(카페·맛집·팝업)는 `/admin/places` API로 등록·수정·삭제·복구가 가능하지만, 이를 다룰 관리자 화면이 없다. 운영진이 Swagger를 직접 호출하거나 개발자에게 요청해 콘텐츠를 등록하는 상태로 보인다.

이 기능의 목적은 운영진이 개발자 개입 없이 홈 화면에 노출되는 성수 콘텐츠를 직접 등록·수정·삭제·복구할 수 있게 하는 것이다.

## 범위

**포함**

- 장소(카페/맛집/팝업) 등록, 수정, 삭제, 복구
- 요일별 영업시간·브레이크타임 입력
- 팝업 전용 운영 기간 입력
- 주소·좌표 텍스트 직접 입력 (VWorld 연동 없음)
- 등록된 장소 목록 확인 (mock 데이터 기반)

## 사용자 시나리오

1. 운영진이 새로 오픈한 성수 팝업을 썸네일·영업시간·운영 기간과 함께 등록한다.
2. 운영진이 기존 지점의 영업시간이 바뀌어 요일별 일정을 수정한다.
3. 운영 기간이 지난 팝업을 목록에서 삭제한다.
4. 잘못 삭제한 장소를 다시 활성 상태로 복구한다.

## 화면 목록과 역할

| 화면 | 역할 | 완료 후 이동 |
| --- | --- | --- |
| 장소 목록 | 등록된 장소를 타입별로 필터링해 확인 (mock 데이터) | - |
| 등록/수정 폼 | 이름·주소·좌표·역 정보·타입·요일별 일정·(팝업)운영기간·썸네일 입력 | 저장 후 목록으로 |
| 삭제 확인 | 선택한 장소를 삭제 처리 | 확인 후 목록으로 |
| 삭제된 장소 보기 | 생략 — placeId 직접 입력으로 복구 테스트 | 복구 후 목록으로 |

장소 목록은 mock 데이터로 보여주고, 삭제된 장소 보기는 placeId를 직접 입력해 복구 API만 테스트하는 것으로 단순화한다.

## 기능 요구사항

**등록/수정**

- `type`(CAFE/RESTAURANT/POPUP)은 등록 후 변경 불가 — 타입을 바꾸려면 기존 장소를 삭제하고 새로 등록
- `weeklySchedules`는 7개 요일을 모두, 중복 없이 포함해야 함
- 요일마다 `BUSINESS` 구간이 1개 이상 필요, `BREAK_TIME`은 `BUSINESS` 안에 포함되어야 함
- `type=POPUP`일 때만 `operationPeriod`(시작일/종료일)가 필수, 다른 타입은 전달하지 않음
- `name`·`station`은 공백 제외 1자 이상, `name` 50자 / `station` 100자 이하
- 영문 필드(`nameEn`/`addressEn`/`stationEn`)는 선택이며 생략하면 한국어 값으로 대체되어 노출됨
- PUT 수정은 전체 교체이며, 영문 필드를 생략하거나 null로 보내면 기존 값이 지워짐 — 수정 폼은 기존 값을 채워 항상 함께 전송

**영문 필드 입력 방식 (결정)**

`nameEn`/`addressEn`/`stationEn` 자동 생성은 하지 않고, 운영진이 등록/수정 폼에서 직접 입력하는 방식으로 결정했다. 주소/번역 API 연동과 그에 필요한 백엔드 중계 엔드포인트 작업은 이번 범위에서 빠진다.

**주소·좌표 입력 방식 (결정)**

VWorld 연동 없이 주소와 좌표를 텍스트로 직접 입력받는다. 위도/경도는 지도에서 좌표를 복사해 숫자로 입력한다.

**썸네일 업로드 방식 (결정)**

Swagger와 프로즈 스펙 문서 그대로 `request`(JSON)와 `thumbnail`(바이너리)을 한 번에 멀티파트로 보내는 파일 첨부 방식으로 구현한다. 이 코드베이스의 다른 기능(S3 업로드 후 URL 참조)과는 다르지만, 이 API는 바이너리 직접 전송으로 고정한다.

**에러 처리 (결정)**

코드로 알고 있는 오류(`PLACE400-INVALID_REQUEST`/`INVALID_SCHEDULE`/`INVALID_COORDINATE`/`INVALID_STATION_INFO`, `PLACE401-UNAUTHORIZED`, `PLACE403-ADMIN_ONLY`, `PLACE404-NOT_FOUND`, `PLACE409-ALREADY_DELETED`/`ALREADY_ACTIVE`)는 전용 메시지를 보여주고, 그 외 미문서화된 오류는 공통 폴백 메시지("요청을 처리할 수 없습니다. 잠시 후 다시 시도해주세요")로 보여준다.

**인증/권한 처리 (결정)**

이 기능의 API 5개는 모두 ROLE_ADMIN 인증이 필요하다. 이미 `/admin` 영역 자체가 로그인한 운영진만 들어오게 막아둔 구조라서, 화면별로 추가 권한 분기는 만들지 않는다. 백엔드가 401 또는 403을 돌려주면 공통 폴백 메시지로 처리한다.

**삭제/복구**

- 삭제는 soft delete이며, 이미 삭제된 장소를 다시 삭제하면 `PLACE409-ALREADY_DELETED` 오류
- 이미 활성인 장소를 복구하면 `PLACE409-ALREADY_ACTIVE` 오류
- 삭제된 장소는 상세 조회(`GET /admin/places/{placeId}`)에서도 조회되지 않음 — 복구 대상을 어떻게 찾을지는 열린 이슈 참고

## 데이터 요구사항

PLACE(장소) 1건이 WEEKLY_SCHEDULE(요일별 일정) 7개를 가지고, 각 일정이 TIME_RANGE(영업/브레이크타임 시간단위)를 가지는 1:N 구조다. 사용자 찜 기능은 PLACE_FAVORITE로 유저-장소 다대다 관계로 별도 관리된다. 등록/수정 폼에 필요한 전체 필드는 이 구조를 역추정한 것이고, 실제 컬럼 이름은 백엔드 코드 확인이 필요하다.

전체 구조는 [성수 콘텐츠 데이터 구조](https://claude.ai/code/artifact/a10b9385-0ca9-404d-a947-6a685bad7dda) 아티팩트를 참고.

## 열린 이슈 및 확인 필요

아래 3가지는 백엔드가 아직 확정하지 않았지만, [장소 관리 백엔드 API 가정 명세서](https://claude.ai/artifact/G4HL5xKnW9yfEAxgWvj2k6)에 합리적으로 가정한 스펙을 적어뒀다. 지금은 이 가정대로 mock과 화면을 만들고, 실제 백엔드가 다르면 두 문서를 함께 수정한다.

| 이슈 | 영향 | 확인 방법 |
| --- | --- | --- |
| 관리자용 장소 목록 조회 API 없음 (백엔드 논의 필요) | 목록 화면은 mock 데이터로 우회해 진행 — 실 서비스 반영 시에는 필요 | 가정 명세서의 GET /admin/places 스펙대로 mock 구현 — 실 서비스 전 백엔드와 대조 필요 |
| 삭제된 장소를 조회할 방법 없음 (백엔드 논의 필요) | 복구 화면 대신 placeId 직접 입력으로 복구 API만 테스트 | 가정 명세서의 GET /admin/places/deleted 스펙대로 mock 구현 — 실 서비스 전 백엔드와 대조 필요 |
| 등록 중 일부 저장 실패 시 트랜잭션 범위/오류 코드 미정 (백엔드 논의 필요) | 썸네일은 저장되고 장소는 실패하는 등 부분 실패 시 화면 처리 방식을 정할 수 없음 | 가정 명세서의 트랜잭션/오류 코드 정책대로 구현 — 실 서비스 전 백엔드와 대조 필요 |

이 항목들은 가정 명세서에 정리해뒀고, 지금은 그 가정대로 구현한다. 실 서비스 반영 전에는 백엔드와 반드시 대조해야 한다.

## 완료 기준

- 운영진은 로그인 후 성수 콘텐츠를 등록·수정·삭제·복구할 수 있다
- 등록/수정 시 위 기능 요구사항의 검증 기준이 화면에서도 동일하게 적용된다 (예: 요일 7개 미입력 시 저장 불가)
- 삭제된 장소는 목록에서 사라지고, 복구하면 다시 노출된다
- PLACE4xx/PLACE409 계열 오류가 발생하면 사용자가 이해할 수 있는 메시지로 노출된다
- Jest 단위 테스트와 Playwright e2e로 등록→목록 노출→수정→삭제→복구 전체 흐름이 검증된다
- 장소 목록 화면은 mock 데이터 기준으로 동작한다
